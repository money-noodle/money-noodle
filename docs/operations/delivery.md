# Delivery and operations standards

## Operating model

The laptop is a development client, never a production host, scheduler, control plane, or sole canonical state location. Developers may run bounded projects and disposable dependencies locally, not the full integrated platform. Remote environments remain observable and recoverable without a laptop and evolve through small compatible deployments.

The only standing environment classes initially are local development and production. CI may create disposable test dependencies, but there is no required persistent preview or staging environment. Validation that cannot safely occur against production must run locally or in isolated ephemeral CI resources before merge.

The API platform is central to every interface, with web as the primary initial presentation. Keep APIs interface-neutral so mobile, desktop, game, and MMO clients use the same authority and contracts. Prefer isolated serverless functions, containers, and managed jobs. Keep user request paths separate from work and maintenance. Production status, deployed versions, health, queues, jobs, leases, reconciliation, data quality, and incidents must be discoverable through scoped operational views.

## CI/CD

CI/CD is mandatory for every deployable project, shared package, infrastructure module, schema, and governed documentation set. Pull requests validate affected boundaries and integration through applicable formatting/linting, types, tests/coverage, contracts/schemas, builds, dependency/secret scanning, infrastructure plans, migrations, and docs/diagram checks.

`main` is the sole integration and production branch. Once delivery is remotely configured and validated, merging to protected `main` automatically invokes production artifact publication and the authorized delivery path; the implemented shape of that path is [below](#implemented-merge-triggered-path). GitHub Actions may orchestrate provider-native automation, but every stage and final verification reports to the commit. Only a qualifying merge under the staged contract below supplies its exact release permissions; agents do not merge without explicit instruction, and the temporary sole-maintainer integration exception is not agent merge authority.

Current repository ownership, host controls, protected-environment configuration, hosted baseline evidence, and deployment gaps are owned in [`../current-status.md`](../current-status.md). These current facts are evidence for the requirements below, not a substitute for them. [`../development/version-control.md`](../development/version-control.md#temporary-sole-maintainer-integration-exception) owns the stable temporary-exception policy and retirement procedure.

Prefer immutable attributable artifacts built once and deployed after gates. If a provider builds from source, pin inputs, run an equivalent production build in CI, and retain artifact/commit attestation. Use reviewed idempotent infrastructure as code, backward-compatible schema/contracts, and independent project deployment. Maintain tested rollback/restore. For an affected deployed component, release completion requires its applicable deployment, migration, health, smoke and observability evidence. Repository-only work has deployment not applicable and does not wait for a nonexistent deployment. Failed health or verification consumes only an explicitly granted conditional rollback slot when its preconditions hold; otherwise automation halts and exposes the blocked state. Do not require progressive rollout or a post-merge manual approval by default.

Protect `main` with one required reviewer and all required checks, no direct push/history rewriting, deployment concurrency, and serialization for unsafe infrastructure/schema operations. The temporary exception leaves those configured controls in place and allows only the maintainer personally to waive the unavailable independent-review gate's two approval subgates: the required approving review and last-push approval. Stale approval never qualifies, and stale-review dismissal remains in force. Conversation resolution and every required check on the pull request's exact current head remain mandatory; any head change invalidates all previous required-check and exception-evidence qualification. Durable evidence identifies the exact head and approval subgate or subgates waived. The exception never permits a conversation, failed-check, or any other protection bypass. Restrict workflow permissions by default. Every action reference is pinned to an immutable commit, and every externally downloaded binary is exact-version and checksum verified before execution. Public pull-request jobs are read-only and hold no OIDC/provider authority; never use `pull_request_target` to execute contributor-controlled source.

## Public automation boundary

Repository source, issues, pull requests, commit metadata, Actions logs and summaries, artifacts, and caches are public or potentially externally observable. They must not carry secret payloads, customer or production data, billing/account identifiers, private recovery material, durable provider credentials, production snapshots, raw state, or unredacted incident evidence. Use synthetic inputs and redacted evidence, and route vulnerabilities or accidental disclosure through [`../../SECURITY.md`](../../SECURITY.md).

Untrusted contribution code may compile, test, build containers, and run offline mocked-provider checks with read-only repository access. It may not receive an OIDC token, provider credential, protected environment, repository write permission, or deployment authority. A successful pull request check is evidence for review only.

Provider authentication is default-deny and short-lived. The workload-identity conjunction accepts only the immutable repository identity, protected `refs/heads/main`, exact `.github/workflows/delivery.yml`, and the closed `push`, `workflow_dispatch`, and `schedule` event set. The scheduled exception reaches only the declared read-only drift path. Production apply and rollback additionally require separately configured federation/provider inputs and apply authorization, recorded verification of the protected `production` reviewer rule, and the environment approval; apply also requires a typed confirmation. The temporary integration exception cannot itself authorize provider authentication, apply, rollback, or deployment; production consent is always the separate environment decision described under human authority below. [`../current-status.md`](../current-status.md) records whether those inputs and provider paths are currently enabled.

## Agent execution and human authority

Agents are intended technical operators for routine checks and, once configured, routine operations. They execute only reviewed automation with short-lived identity, least privilege, deny-by-default inputs, bounded side effects, independent post-operation verification, and durable redacted evidence. An agent or workload identity does not convert a plan, issue assignment, green check, prior integration bypass, evidence record, or broad standing instruction into integration or production authority. It cannot invoke or request the temporary sole-maintainer exception, perform an exception merge, or use that policy to bypass provider or deployment controls.

Humans retain provider and domain account ownership, root recovery, break-glass custody, and explicit scoped approval for production effects. The environment gate is unchanged: the maintainer is the only required reviewer and `prevent_self_review=true`. Under the principal's 2026-09-18 sole-maintainer decision (#74) no second approver is required for M1. The maintainer approves a deployment another actor initiated through the ordinary environment review. A deployment initiated by the maintainer's own merge to `main` waits at the gate until the maintainer personally uses the environment administrator bypass for that exact deployment; merge-triggered delivery is therefore automatic up to the gate and one deliberate maintainer action beyond it. No agent, workload identity or automation may use, request or assume that bypass, and a PR merge alone is not production consent. [`../current-status.md`](../current-status.md) owns the current protected-environment configuration. Routine work must not bypass reviewed automation through a cloud console, ad hoc provider command, resident laptop process, or locally held durable credential. The explicitly reviewed one-time bootstrap and authorized recovery procedures are bounded exceptions; reconcile every resulting change into code and remote state.

The accepted [`production-control-plane.md`](production-control-plane.md) defines the versioned operation catalog, exact approval grant, CI/CD versus administrative-job versus read-only operational-API surfaces, independent verification, durable evidence, bootstrap/break-glass bounds, and payload-blind secret lifecycle. It is the decided boundary shape under Working [`ADR-0010`](../architecture/decisions/ADR-0010-agent-operated-production-control-plane.md), not a running control plane: none of its controls are implemented or remotely validated, so it grants no production authority, and building and remotely validating them remains separate work that has not started. The current environment gate remains unsatisfied; the accepted sole-principal target below is not an applied host change.

## Current-to-target activation

The principal-accepted [#68 packet](https://github.com/money-noodle/money-noodle/issues/68#issuecomment-5656747952) defines a sole-human review/merge target, not enabled automation. The principal is the human reviewer and merger; agents implement and independently technically review; bounded workload identities execute and separately permissioned readers verify. An agent technical review is not a second human. The [source publisher](../development/version-control.md#restricted-workload-source-publication-target) must genuinely author/push the reviewed candidate; approving token-created PR workflows is CI admission, not production consent.

| Gate | Required qualification / authority |
| --- | --- |
| Current controls | Keep current provider paths disabled and production reviewer/self-review safeguards unchanged. Production consent is the maintainer's environment review, or the maintainer's personal administrator bypass for a self-initiated deployment (#74); it cannot be replaced by this policy or its own publication. |
| Reviewed source | Integrate #68 policy and independently tested #70 provider-disabled adapters, consuming #69's runtime contract. #71 artifact, #72 telemetry and #73 delivery assembly gates follow. No host/provider proof is needed to write that source. |
| Host transition (#74) | Separately authorize and observe real workload author/pusher, native CI admission, exact review-head/base/test-merge/check relation, stale and last-push approval, conversation resolution and principal merge. Record the `production` protection rules and observe, with provider inputs disabled, both the maintainer-approvable path and the self-initiated path. Qualify replacement grant enforcement before changing any environment gate. Retirement of the integration exception's host bypass surfaces follows agent identity (#156). No agent bypass or alternate credential fallback. |
| Exact operation approval (#75) | Bind future exact source/helper/dependency, IaC/saved plan, artifact/configuration, finite targets/effects, expiry, verifier, cost assumptions/limits, custody and recovery. Policy acceptance and green CI are not this consent. |
| Trust bootstrap (#76) | Principal executes only the enumerated once-only HB genesis/witness, state/federation and private-input manifest; independently verify partial effects, token mint/submission limits and negative access. No assumed constrained agent runner. |
| Provider validation (#8), milestone acceptance (#77) | Perform only separately authorized remote operations and record dated actual denial, status/rendering/trace, recovery and bounded audit evidence. Local mocks do not satisfy these gates. |

After all applicable transitions are integrated, authorized and qualified, a qualifying protected-main merge automatically initiates the exact reviewed release bundle without a second routine human deployment approval. The bundle separately consumes qualifying artifact publication, one forward vector (at most two services) and **one conditional rollback vector** only when verified predecessors exist, all under the original consent and expiry. [Catalog v2](production-control-plane.md#m1-catalog-v2--selected-not-enabled) owns exact slots, tuple bindings, journal/witness and recovery. Infrastructure, configuration, access, telemetry, cost, secret, bootstrap, destructive and exceptional effects have separate authority; merging an application release does not grant them. Changing source/configuration/digest, target, count, owner or expiry is not a retry.

Current source does not implement this replacement. In particular existing `delivery.yml` typed apply and protected-environment gates, the unapplied OpenTofu public-IAM option and latest-traffic assignment are not private-before-public qualification. #70/#73 must reconcile them before enablement; no workflow, IaC, provider variable, secret, journal or host setting is changed by #68.

## First-release acceptance and exposure order

The initial control artifact is pinned reviewed workflow/helper source plus its complete executable dependency closure in Git history, not a new OCI controller or assumed constrained runner. Bind each affected project's build target/platform, reviewed source, immutable configuration version/digest, builder/invocation, image digest, provenance, SBOM and scans. Deploy the verified artifact once; no rebuild during promotion or rollback. Preserve #69's production `NODE_ENV`, credential-free HTTPS `PLATFORM_API_ORIGIN`, separate `ARTIFACT_VERSION` release label and `MONEY_NOODLE_COMMIT` full source SHA. Infrastructure-rendered configuration must still pass the existing real runtime-reader/composition bridge; it is not deployed-revision proof.

Compute affected projects from declared build/runtime/contract dependencies. API-only compatible changes need not redeploy web; web-only compatible changes need not redeploy API. A coordinated compatible contract change deploys API first, verifies it, then web; removal waits until consumers no longer depend on the old contract. Record the exact ordered vector, predecessor compatibility and per-step verification. Unaffected services remain unchanged and independently healthy.

#### Implemented merge-triggered path

`.github/workflows/delivery.yml` implements that rule as two jobs, and this is the only deployment initiation: there is no interim `workflow_dispatch` deployment.

- `release-plan` is credential-free — no OIDC token, no environment, no provider input. It establishes the reviewed predecessor of the push and **fails closed** when that range is undecidable: an absent or all-zero previous commit, a commit missing from the checkout, or a previous commit that is not an ancestor of this head all refuse rather than fall back to "everything changed". It then computes the affected projects from the workspace project graph and maps them onto the `metadata.deployment` block each deployable project declares in its own `project.json`. Declaring that block is what makes a project deployable; the pipeline holds no service table. An affected project nothing declares, an ambiguous manifest set (a repeated unit or order, an undeclared dependency, a unit ordered before something it depends on), or more affected units than the catalog's `service.deploy` row allows produces no vector at all.
- `deploy` runs only for a `push` to `refs/heads/main` whose head is the qualified head, whose publication succeeded, whose vector is non-empty, and with all four authorization states recorded true. It holds exactly the permissions the manual apply holds, waits at the same `production` environment gate, and masks account identifiers with the same rules. It resolves and provenance-verifies **every** digest in the vector before applying any of it: the tag this commit published is only a lookup, and the digest behind it is accepted only when `gh attestation verify` binds it to this repository, this exact signer workflow, `refs/heads/main` and this source commit. Nothing is rebuilt for promotion.
- Each unit is applied, its service URI read, and then probed with a short-lived ID token bound to that service as its audience — the services are private, so an anonymous probe is refused. The API's probe exercises the published contract, not only readiness. Step order is the declared order, and a failed step ends the job, so a failed API verification leaves web untouched.
- The path is forward only. It names no rollback revision and spends no recovery slot; `service.rollback` requires a verified predecessor, which cannot exist before a first deployment. Recovery is [#155](https://github.com/money-noodle/money-noodle/issues/155).
- The job records the ordered vector, the permission slot spent, which services were left unchanged, what was verified at each step, and that no predecessor evidence and therefore no rollback permission exists. It publishes no service URI, digest or account identifier, because a job summary is public and never masked.

#### Packaged-artifact journey gate

`tools/release.test.mjs` is the attachment point: `pnpm verify:foundation` already runs `node --test tools/*.test.mjs`, so the nested `tools/release/**` suite executes inside the existing `affected projects and repository gates` required check. It fails when nothing was discovered, when a nested check failed, and when the packaged journey was enabled for that run and reported itself skipped.

The journey itself runs inside the existing `container web` required check, against the images that job built and scanned — no required check is added or renamed, because the release qualification gate waits for exactly the four names the branch protection rules own. An exact-version, lockfile-pinned, test-only Playwright dependency supplies the browser; the browser revision is the one that release declares, and it is installed in the journey step rather than assumed from a runner image. Its integrity rests on the lockfile's integrity hash for the package that pins the revision and on the vendor's HTTPS distribution, not on a checksum this repository verifies: the vendor publishes no per-archive checksum to pin. That is a narrower guarantee than the checksum-verified Gitleaks download, it is recorded here rather than implied, and it applies only to a credential-free pull-request job that holds no provider authority.

Failure is injected by a CI-only upstream fixture between the two packaged artifacts, never by a production endpoint or an application test switch. The fixture terminates TLS with a certificate minted for the run, which the packaged web artifact trusts through `NODE_EXTRA_CA_CERTS` — certificate verification stays on. In its pass-through mode it is also the recorder, so the timestamp the page is checked against is the one that exact request received from the packaged API, not one from an unrelated request. The normal journey asserts the platform state as accessible text and that timestamp; a timeout, a transport failure, a malformed response and an incompatible schema each assert `Status unknown` with no invented available, zero-like or stale value.

First creation has a stricter order:

1. **Create private API.** Cloud Run v2 `POST /v2/projects/{p}/locations/{l}/services?serviceId={id}` uses the approved digest/configuration, invoker check enabled and no public IAM. Runtime identity/probe access require enumerated prior authority; service creation does not grant IAM.
2. **Independently verify private API.** Read Service/known Operation and IAM using a separate read-only identity. Invoke bounded health/status probes with an **audience-bound ID token**, not an Admin API access token. Verify readiness, exact status schema/source time, digest/configuration and denial of anonymous invocation. Inspect native UID/name, generation/observed generation, terminal condition, reconciling and etag privately; journal only safe comparisons. Startup readiness alone is insufficient.
3. **Expose API under separate H2.** `POST /v2/{service}:setIamPolicy` with fresh expected etag adds exactly `allUsers`/`roles/run.invoker`; independently verify effective policy and the public contract. No broad overwrite or invoker-check bypass.
4. **Create and verify private web.** It uses the now-public API normally; no runtime web ID-token feature is introduced. The verifier authenticates to private web, confirms anonymous denial, checks rendering and the API-provided time, and verifies artifact/configuration.
5. **Expose web under separate H2.** Apply the separately approved exact public-access delta; independently verify public rendering and IAM policy.

Private probes consume bounded requests/resources: private is not zero traffic. Existing Cloud Run configuration assigns 100% latest traffic separately from public IAM; traffic readiness does not prove independent pre-exposure validation. Before exposure, failure leaves the private candidate blocked, with no ungranted deletion or rollback. No predecessor means no rollback. After exposure, access correction may consume only a **previously explicit finite H2 inverse** under its original expiry; otherwise stop the affected path. Ordinary releases with verified predecessors use the single conditional rollback slot, independently verified; there is no invented forward-recovery digest. Ambiguous effects never replay: catalog quiescence and old-owner exclusion govern even after cancellation or new approval.

### Status, rendering and trace evidence

The actual API-owned [OpenAPI v1 schema](../../services/platform-api/openapi/platform-api.v1.yaml), not a subset health check, is the acceptance source. `PlatformStatus` and nested `service` disallow additional properties and require exactly:

| Field | Required value / bound |
| --- | --- |
| state | `available`, `degraded`, or `maintenance` (never API `unknown`) |
| asOf | UTC RFC 3339 source observation time, generated by API, not substituted by web/runner time |
| service.name | `platform-api` |
| service.version | 1–64 characters, `^[A-Za-z0-9][A-Za-z0-9._+-]*$`; approved release label, not assumed SHA/digest |
| schemaVersion | literal string `1` |
| requestId | 1–128 characters, `^[A-Za-z0-9._:-]+$`; bounded correlation identity |

Verify response headers/correlation, HTTP result and full schema. Health responses separately require exactly `status` (`live` or `ready`), `service` (`platform-api`) and the bounded `version`. Error responses follow the declared RFC 9457 Problem contract (`type`, `title`, `status`, `errorCode`, `requestId`; optional `detail`/`instance`), never raw provider diagnostics. Provider digest/configuration evidence stays in the operation record; do not expand the public DTO with topology or sensitive identifiers.

Measure API source time against a bounded verifier request window and declared clock-skew/freshness tolerance from the exact validation manifest. Prove the web displays that same API-provided time and accessible state text, not color alone. API timeout, transport failure, incompatible schema and invalid response must render **status unknown**, with no invented available, zero-like or stale fallback; exercise each bounded failure fixture. Current web performs one no-store generated-client request with a 1500 ms default timeout and no retry fan-out. Failure injection into a live service needs its own exact operation authority; provider-free fixtures alone are not remote evidence.

One normal browser journey and one forced-failure journey must each have attributable web/API spans with shared W3C trace context and request ID, service/deployment identity, source/artifact version, bounded route/latency/outcome metadata and source/as-of evidence. Deliberately inject a synthetic forbidden marker and prove no bodies, credentials, disallowed headers or personal data reach logs/traces/public artifacts. Telemetry outage is degraded observability, not healthy evidence and not itself rollback authority. Record sample, exclusions, uncertainty and largest validity threat. Quantitative service objectives require dated remote baseline evidence, not invented local thresholds.

### Foundation denial and recovery qualification

Before provider enablement, separately authorized qualification must prove unauthorized refs, forks, workflows and identities cannot exchange delivery credentials; the executor cannot read runtime secret values; web cannot read registry/state; API cannot deploy or write state; and missing/invalid provenance denies deployment. No provider key or secret payload may appear in Git, images, public runner output or handoffs. Future secret introduction remains separately gated on rotation/revocation and payload-blind custody tests; M1 creates no test secret by implication.

The exact pinned infrastructure toolchain must match CI. Prove real concurrent applies to one stack block rather than interleave, versioned state restores, out-of-band drift is reported rather than auto-corrected, and applying web neither locks nor modifies API state. Test reconstruction in a separately authorized disposable scope, publishing no raw plan/state. Both services require independent health and attributable versions; rollback with a verified predecessor must leave unaffected services healthy. Later domain cutover separately verifies TLS issuance/renewal. These requirements remain future evidence, not assertions that source tests have proved provider behavior.

## Cost estimates and operational bounds

There is no current normative USD 30 ceiling. Use [#85's accepted 2026-09-09 revision-3 cost research](https://github.com/money-noodle/money-noodle/issues/85) as dated synthetic known components **plus unknowns**, not a platform total, invoice, guaranteed free allowance, spending authorization or replacement fixed ceiling. Revalidate rates, units, region, billing period, shared pools, other workload usage and private eligibility at #75's exact revision. Keep currencies and migration phases separate; M1 does not inherit later retained-provider consumers or costs.

Measure and attribute usage/cost by service, revision/artifact digest, phase, operation/run, accountable owner, currency and SKU, with source/region/billing period and as-of. Private account mappings remain private; public reports use safe aggregates. Include probes/startup/shutdown, poll sender, independent verification, control traffic, artifact/state retention and egress, not just user requests. Missing measurement is unknown, not zero.

The exact manifest sets finite max/min instances, concurrency, request/operation deadlines, retry and polling budgets, temporary-resource lifetime, artifact/state-version retention, telemetry sampling/cardinality/retention and cleanup authority. Global M1 provider concurrency and journal budgets come from the catalog. No ambiguous mutation retry or unapproved retention deletion is permitted. Configure actual/forecast gross-spend, per-SKU growth, allowance-headroom, egress, temporary-age and freshness alerts with owner, window and escalation; independently verify notification tests. Alerts are **not a guaranteed spending cap** and never imply billing detachment or automatic shutdown authority. Missing inputs or unexplained deltas stop the affected new operation for review, not a healthy application.

The existing unapplied `infra/modules/budget-guardrail` USD 25 alert-budget and 20/50/80/100 alert-threshold defaults and associated static tests describe source defaults only; they are not the current budget policy, observed spend or an applied cap. #70 reconciles provider-disabled configuration; #75 approves exact settings. Preserve [dated composition evidence](deployment-composition.md) rather than rewriting its historical estimates. Telemetry retention targets remain explicit, including the existing provider configuration gaps; audit/spent-grant history is not disposable telemetry.

## Independent deployment and dependencies

Every project is independently buildable, versioned, deployable, observable, and rollback-capable. Each project owns a machine-readable manifest of build dependencies, runtime dependencies, API/event/schema contracts, compatible version ranges, deployment unit, health checks, and owned data/schema. CI computes the affected dependency graph from declared manifests and changed contracts; it does not guess from runtime traffic.

A deployed service reports source/artifact version, configuration/schema version, health, and dependency compatibility without exposing secrets. At runtime it checks declared dependencies and degrades or fails clearly when required capabilities are absent or incompatible. It must not discover new authority dynamically or silently coordinate through another service's database.

The delivery pipeline deploys only affected projects and dependents requiring coordination. Prefer backward-compatible contracts so dependencies can deploy independently; when coordination is unavoidable, CI produces an explicit ordered plan and verifies every step. The operational view shows project deployment state, versions, dependencies, compatibility, and rollback/recovery status.

Each service exclusively owns its database schema and data and uses a least-privilege database role. Other services use its API/events or an explicitly owned projection rather than reading or writing its tables. A service ships and runs its own versioned migrations as part of its deployment and provides a tested rollback or forward-recovery plan. Migration execution is single-owner and concurrency-safe, not an uncontrolled startup action by every replica. Expand/contract compatibility must allow safe application rollback whenever possible; destructive or irreversible migrations require backup, restore validation, and an explicit coordinated plan.

## Secrets and infrastructure

The first composition selects Google Secret Manager, OpenTofu, separate GCS-backed state, Cloud Run, Artifact Registry, federated GitHub Actions trust, and provider-native OpenTelemetry ingestion; the accepted decisions and dated comparison evidence are in [`deployment-composition.md`](deployment-composition.md) and ADR-0004 through ADR-0007. That composition is implemented as reviewable configuration in [`../../infra/README.md`](../../infra/README.md) and **has not been applied**; the one-time procedure and the exact identifiers the maintainer must supply are in [`../../infra/bootstrap.md`](../../infra/bootstrap.md). Until the complete validated bootstrap repository-variable contract exists, every provider-touching job in `.github/workflows/delivery.yml` is skipped. Apply and rollback additionally require explicit apply authorization, a recorded verification that the `production` environment really has required-reviewer protection, and the environment gate itself; apply also requires a typed confirmation. Naming an environment in workflow YAML is not treated as proof that GitHub configured its protection. Infrastructure definitions and desired configuration live in source control. Mutable infrastructure state lives in an encrypted durable remote backend with concurrency locking, versioning, and backup; never commit raw state to Git. Detect and surface drift against the source-controlled desired state, and keep reconstruction/reconciliation procedures tested.

Every operational secret has a durable source of truth in an approved managed secret store or equivalent encrypted durable system; laptop environment files are never canonical or unique. Document owner, access, rotation, recovery, and revocation. OpenTofu may declare secret containers, IAM, lifecycle policy, and references but must not receive a payload or manage a value-bearing version that would persist in plan or state. Provider-generated values are created inside the managed boundary; externally supplied values use a private payload-blind ingress. Until that ingress exists, direct human entry in the provider's protected secret interface is an explicit audited payload-ingress exception, not a routine agent operation.

Prefer short-lived workload identity and CI federation over long-lived cloud keys. Delivery receives only project/environment-specific secrets; developers use separate least-privilege access. Never commit, print, or expose secret values in status views, logs, artifacts, or handoffs.

Manual provider changes and click-only infrastructure are exceptions requiring reconciliation back into code. Never deploy around the pipeline or trigger provider automation manually without explicit authority.

## Maintenance and recovery

Run lightweight bounded health, reconciliation, cleanup, retention, and integrity work during operation. Keep it isolated, resumable, retry/overlap safe, and observable. Automatic recovery is the primary path; authorized audited administrative repair and break-glass access are fallbacks.

Define service and data-class availability, consistency, RPO, RTO, backups, restore tests, and incident behavior before production authority. A failed dependency degrades explicitly rather than presenting stale or unknown state as healthy.
